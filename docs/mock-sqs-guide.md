# SQS Mock 데이터 전송 가이드 (QA용)

비전 파이프라인(카메라/모델) 없이 `vision-summary-schema.json` 계약에 맞는
mock summary를 생성해 SQS로 전송하는 도구입니다. 수신 측(서버/백엔드) QA에 사용하세요.
구현은 루트의 `mock_sqs/` 모듈에 있으며, 스키마·큐 설정은 실제 파이프라인과 동일한 것을 공유합니다.

## 실행 방법 (둘 다 동일하게 동작)

```bash
python main.py --mock-sqs [옵션...]     # main.py 플래그로 트리거
python -m mock_sqs [옵션...]            # 모듈 단독 실행
```

큐 URL/리전/자격증명은 실제 전송과 동일하게 `.env` → 환경변수 → config 순으로 해석됩니다
(`SQS_QUEUE_URL`, `AWS_REGION`, `AWS_ACCESS_KEY_ID` 등. 코드에 하드코딩하지 않음).

## 옵션

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--scenario` | `normal` | 데이터 시나리오: `quiet`(한산, 0명 빈발) / `normal` / `peak`(붐빔) / `stress`(대량, 평균 60명) / `daily`(한산→피크→한산 시간대 변동) / `weekly`(실측 기반 일주일치 backfill, 아래 별도 절) |
| `--count` | 12 | 전송 건수. **0 = 무한 스트리밍** (Ctrl+C로 종료) |
| `--interval` | summary 주기(5초) | 전송 대기 시간. **0 = 대기 없이 연속 전송** (벌크 적재용) |
| `--seed` | 없음 | 랜덤 seed. 같은 seed면 같은 데이터 재현 (timestamp 제외) |
| `--start-seq` | 1 | 시작 seq 번호 |
| `--wave-period` | 60 | `daily` 시나리오의 변동 주기 (메시지 건수, 60건=5분 분량) |
| `--days` | 7 | `weekly` 시나리오의 생성 일수 |
| `--start-date` | days일 전 | `weekly` 시작 날짜 (YYYY-MM-DD, KST). 기본값이면 어제까지의 최근 일주일을 backfill |
| `--board-id` / `--device-id` | 시나리오 기본값 | 메시지 식별자 덮어쓰기 (config 파일은 변경하지 않음) |
| `--out` | - | **SQS 전송 대신 파일로 저장** (`.jsonl` / `.jsonl.gz` / `.json`) |
| `--dry-run` | - | 생성+스키마 검증+JSON 출력만 하고 전송 생략 |
| `--no-final-partial` | - | 종료 시 짧은 마지막 window(실제 finalize 재현) 전송 생략 |

기본 실시간 모드(`--interval`이 0이 아님)는 실제 전송 시각을 `timestamp`로,
직전 메시지 이후 실제 경과 시간을 `interval_sec`로 넣습니다. 따라서 전송 처리 시간이
누적되어도 timestamp가 현재 시각에서 밀리지 않습니다. `--interval 0` 벌크 적재만은
5초 논리 시계를 사용해, 대기 없이도 연속된 5초 window 데이터를 생성합니다.

## QA 시나리오별 사용 예

```bash
# 1) 전송 없이 데이터 형태 확인
python main.py --mock-sqs --dry-run --count 3 --seed 42

# 2) 단건 연결 확인 (MessageId 출력)
python main.py --mock-sqs --count 1

# 3) 실시간 대시보드 QA: 시간대 변동 곡선을 5초 간격 무한 스트리밍
python main.py --mock-sqs --scenario daily --count 0

# 4) 벌크 적재/성능 QA: 대량 인원 500건을 대기 없이 전송
python main.py --mock-sqs --scenario stress --interval 0 --count 500

# 5) 엣지 케이스: 0명 구간·성별/연령 미상 빈발
python main.py --mock-sqs --scenario quiet --count 30

# 6) 일주일치 현실 데이터 backfill (약 9만 건, 배치 전송)
python main.py --mock-sqs --scenario weekly --seed 42

# 7) 전송 없이 파일로만 뽑아 통째로 전달 (압축 권장: 70MB → 1.2MB)
python main.py --mock-sqs --scenario weekly --seed 42 --out weekly.jsonl.gz
```

## 파일로 내보내기 (`--out`)

수신 서버 개발자에게 데이터 묶음을 통째로 넘겨야 할 때 사용한다.
`--out` 을 주면 **SQS로 전송하지 않고 파일로만 저장**한다
(대량 데이터가 실수로 큐에 들어가는 것을 막기 위해 전송과 저장을 겸하지 않는다).

| 확장자 | 형식 | 비고 |
|---|---|---|
| `.jsonl` | 한 줄에 메시지 1건 | 기본. 스트리밍 파싱에 적합 |
| `.jsonl.gz` | 위와 같고 gzip 압축 | 일주일치 70MB → **1.2MB**, 전달용으로 권장 |
| `.json` | 전체를 배열 하나로 | 소량 확인용 (대용량은 비권장) |

저장되는 값은 전송하는 것과 완전히 동일하며(건별 스키마 검증 통과),
같은 `--seed` 면 같은 데이터가 재현된다. 실제 일주일치 출력 검증 결과:

```
[DONE] weekly 7일 = 90720건 ots=98646 lts=4470(4.5%)
[FILE] weekly.jsonl.gz (90720건, 1.0 MB)
```

날짜별 `seq` 1..12960 연속, 하루 1건씩 총 7건의 partial window,
KST 00~06시 구간 공백까지 파일 안에 그대로 재현된다.

## weekly 시나리오 (명동역 인근 보드, 일주일치 backfill)

> 이 데이터가 **어떤 상황을 가정한 것인지**(규모·인구통계·심어둔 이벤트·실측 대 가정
> 구분)는 팀 공유용 문서 [mock-weekly-scenario.md](mock-weekly-scenario.md) 에 정리되어 있다.
> 아래는 실행 방법 중심의 설명이다.

`weekly`는 다른 시나리오와 달리 **과거 일주일치**(기본: 어제까지 7일) 메시지를
timestamp backfill 방식으로 한 번에 적재한다. `--count`/`--interval` 대신
`--days`/`--start-date`를 쓰고, SQS 배치 전송(10건 묶음)으로 보낸다.
설치 위치는 **명동역 인근 상권**을 상정한다.

구조 (실제 운영·파이프라인 동작 재현):

- 식별자는 기존 config 값(`board_gangnam_01` 등)을 그대로 쓴다. 통행 패턴·인구통계만
  명동 상권을 모델링하며, 다른 값으로 보내야 하면 `--board-id` / `--device-id` 를 쓴다
- 운영 시간 매일 **06:00~24:00 (KST)** — 00~06시는 메시지 없음
- 하루 = 세션 1개: `seq` 1부터 재시작, 자정 종료 시 마지막 1건은 partial window
- 평일은 출근(7:30~9:30)·점심(11:30~13:30)·퇴근/저녁(17:30~20:30) 3봉 곡선,
  금요일은 저녁 피크 연장, 주말은 오후~저녁 단봉 (토 1.15× / 일 0.85×)
- LTS 전환율은 시간대별 변주: 출근길(06~10시) 2~4% < 낮 3~6% < 저녁(17시~) 4~7%
  (바쁜 출근길은 주목률이 낮다는 업계 통념 기반 가정)
- 현실감 이벤트 1 — 수요일 우천: 통행 0.7×에 그치지만, 우산이 얼굴을 가려
  **LTS 0.6× + 성별/연령 미상 비율 2배**(0.15→0.30 / 0.10→0.25)로 검출 저하를 재현
- 현실감 이벤트 2 — 토요일 19:00~19:30 근처 행사 스파이크(통행 2×)

값 파라미터는 `data/jsonl` 실측 attention 세션 27개(총 175분) 분석에 근거한다
(`mock_sqs/weekly.py` 상수로 조정 가능):

| 파라미터 | 값 | 실측 근거 |
|---|---|---|
| 피크 시간대 5초당 통행자 λ | 1.7 | **낮(09~15시) 평균이 실측 1.07명/5초와 일치하도록 역산** |
| LTS 전환율 | 2~7% | 자연 관찰 세션 1.8~6.3% (전체 3.6%) |
| dwell | 로그정규(중앙값 2초) | 응시 에피소드 중앙값 1.5~2.2초, <2초 최빈, p90 4.4~6.3초 |

통행량은 **실측 최고치가 아니라 실측 평균에 맞춰** 앵커링했다. 그 결과 평일
하루 통행량은 14,000명 내외(시간당 약 790명 = 2.3초에 1명, 피크 1,170명/시간)이고,
요일 배율·우천·푸아송 노이즈가 겹쳐 실제 일별 값은 아래처럼 흩어진다:

```
월 14,107  화 14,046  수 9,994(우천)  목 14,112
금 16,750  토 17,333  일 12,304        → 주간 98,646
```

단, 실측이 전부 09~15시 촬영이라 출퇴근·심야 배율 곡선은 통행량 상식에 따른
가정이다. 낮 시간대 절대값(λ)만 실측 근거가 있다.

### 인구통계 (명동 상권 기준)

명동은 성격이 다른 두 집단이 겹치므로 단일 분포 대신 **세그먼트 혼합**으로
생성한다 (`mock_sqs/demographics.py` 상수로 조정):

| 세그먼트 | 성비 | 연령 특징 | 근거 |
|---|---|---|---|
| 내국인(중구 직장인) | 남 50 : 여 50 | 40~50대 53% | 서울시 상권분석 길단위인구에서 명동은 40~50대 비중 53% |
| 외국인 관광객 | 남 40 : 여 60 | 20~30대 53% | 방한 외래관광객 여성 약 60%, 중국인은 20~30대 47%·여성 67% |

관광객 점유율은 평일 오전 0.25 → 저녁 0.65, 주말 0.55~0.75로 시간대에 따라
달라진다 (오피스 상권과 관광 상권이 시간대로 갈린다는 통념 기반 가정).
그 결과 주간 전체는 **남 44 : 여 56, 20~30대 46% / 40~50대 42%**로 집계되고,
같은 보드에서도 평일 오전은 40대 이상이, 저녁·주말은 20대가 두터워진다.

## 데이터 품질 보장

mock은 "가상의 통행자 개인"을 만들어 집계하므로 (실제 파이프라인과 같은 구조)
아래 불변식이 항상 성립하며, 매 건 전송 직전 JSON Schema 검증을 통과해야 전송됩니다:

- `lts_count ≤ ots_count` (응시자는 통행자의 부분집합)
- `male.count + female.count ≤ count` (성별 미상 제외 — 실제 집계 동작 재현)
- 성별별 age 버킷 합 ≤ count (연령 미상 제외)
- dwell 분포·합·평균이 같은 dwell 샘플에서 도출 (`avg × lts ≈ sum`)
- `seq` 연속 증가, `timestamp`는 interval씩 가산
- 종료 시 마지막 1건은 `interval_sec < 5`인 partial window (실제 finalize 동작 재현)

값 범위(인원수·응시율·dwell)는 상식적 추정치이며 `mock_sqs/scenarios.py`의
상수만 고치면 조정할 수 있습니다.
